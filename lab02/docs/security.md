# Security boundaries and source-control hygiene

## Never commit

- `BackupAndRestoreAgentDeployment.yaml` generated by the hub UI: contains a time-limited authentication token (our UI displayed **one hour** validity).
- Kubeconfigs, service account tokens, `.kube` directories, login passwords, cloud keys, generated NooBaa OBC credentials, any private `.pem`/`.key`/`.p12` files.
- Screenshots revealing S3 access keys, secret keys or cluster login tokens.
- Full Kubernetes Secret JSON/YAML exports, verbose `oc describe secret` output or log bundles containing credentials.

The repository `.gitignore` is a *defense in depth*, not a guarantee. Inspect `git diff --cached` and use secret scanning before pushing. If a key has been exposed, rotate it; removing a commit does not guarantee the key is private again.

## Credential handling

The NooBaa OBC creates a generated bucket ConfigMap and a Secret containing `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. Read credentials only when entering them in the Fusion Service Protection UI; do not print or copy them into a public script or chat. Stage 02 Ansible reads the OBC Secret under `no_log: true` and writes a Fusion Secret directly to Kubernetes.

Certificate Secrets contain public server certificates but still require correct PEM formatting; stage 02 appends a real newline before base64 encoding. For Service Protection, the manually installed TLS Secret must be in the *hub* Fusion namespace; the OBC secret remains on the second cluster.

## Temporary privileged recovery

The MongoDB restore may have a different OpenShift-assigned UID from the source. The v0.4.4 playbook creates a short-lived `mongodb-repair` service account and Job in the restored namespace, grants `anyuid` only to that account, corrects file ownership only on the restored `mongo-storage` PVC, then revokes the grant and deletes both resources. The repair checks the expected owner UID; it does not remove database files or run MongoDB repair. Monitor cleanup if a run is interrupted during a network/API outage.

## Data preservation

Backups and restores are explicitly named and treated as immutable evidence. Scripts refuse to overwrite unrelated restores or existing unmanaged namespaces, and should be run only against disposable lab workloads. Do not use this repository as a production disaster recovery runbook without formal review and system-specific testing.
